## 1.4 - 2026-09-14
* OpenCart 2.1, 2.3, 3.x, 4.x, карта ПВЗ, память и трафик: ответ карты (`get_points`) содержит каждую точку один раз, а тарифы (название, цена, сроки, тип забора, шаблон кода варианта) — отдельным словарём, точка ссылается на них ключами. Раньше точка повторялась на каждый тариф и тип забора: для Москвы это десятки тысяч записей и мегабайты JSON на один показ карты. На карте одна метка на точку, в балуне все её тарифы с кнопкой «Забрать отсюда» у каждого; код выбранного варианта и `set_point` прежние. Формат ответа изменён без обратной совместимости: `ApishipMap.open(data, callback, code)` принимает весь ответ сервера. Список ПВЗ при редактировании заказа в админке собирается из той же структуры.
* OpenCart 2.1, 2.3, 3.x, безопасность: cron-эндпоинты экспорта и импорта статусов (и `get_delivery_cost_original`) принимают только POST, ключ передаётся заголовком `X-Apiship-Key` (или полем `key` в теле); ключ в URL и запросы GET получают отказ. В настройках модуля показывается пример cron-команды (`curl -X POST -H "X-Apiship-Key: …"`), cron-команды на серверах нужно перенастроить. Действия с заказом из админки (выгрузка, отмена, ярлыки, акты, параметры) авторизуются сессией администратора: POST с `user_token` (`token` в 2.x) и право «Изменение» на `sale/order` — cron-ключ в html админки больше не попадает. Идентификаторы заказов в SQL-запросах приводятся к числу.
* OpenCart 2.1, 2.3, 3.x, безопасность: строки от API (названия ПВЗ, служб, тарифов, статусов, адреса, сообщения об ошибках) экранируются в чекауте, балунах карты и админке; ссылки на ярлыки, акты и трекинг принимаются только `http(s)`.
* OpenCart 2.1, 2.3, 3.x, память и скорость: справочники API, точки и расчёт калькулятора кешируются в кеше OpenCart (общий для магазина, ключ по токену), а не в PHP-сессии покупателя. У API запрашиваются только нужные модулю поля точек (`fields`), индекс точек в кеше разбит на шарды по id, известные точки повторно не запрашиваются, выбранный ПВЗ берётся из индекса; ошибки калькулятора не кешируются. Соединение с API переиспользуется (keep-alive, gzip), нет лишнего пустого запроса при постраничной загрузке. Отладочный лог без полных списков ПВЗ и `pointIds`, с `x_tracing_id` запросов.
* OpenCart 2.1, 2.3, 3.x: данные чекаута модуля (адрес расчёта, выбранные ПВЗ) хранятся в сессии OpenCart, а не в отдельной PHP-сессии.
* OpenCart 2.1, 2.3, 3.x, карта ПВЗ: подписи на карте берутся из языковых файлов, фильтры «тип точки» и «служба доставки» применяются вместе (раньше затирали друг друга), при недоступности Яндекс.Карт модалка закрывается с сообщением.
* Исправлено (OpenCart 2.1, 2.3, 3.x): при редактировании заказа в админке список ПВЗ приходил без заголовков (`title` не заполнялся); распределение веса места по позициям падало на неопределённой функции при расхождении весов.
* Юнит-тесты библиотеки пакетов 2.x/3.x (`make test-oc3`) и проверка синтаксиса на PHP 7.4 и 8.3 (`make lint-oc3`).

## 1.3 - 2026-09-04
* Исправлено (OpenCart 4, админка): при редактировании заказа не менялся ПВЗ — ядро OC 4.1.0.4 (`catalog/controller/api/shipping_method`) проверяет `cost` и `tax_class_id` через `empty()`, и способ ApiShip без класса налога (`tax_class_id = 0`) или бесплатный отвергался с «Необходимо выбрать способ доставки!». Скрипт модалки передаёт нулевые значения строкой `0.0`, которую ядро принимает и приводит к нулю.
* Исправлено (OpenCart 4, админка): после обновления модуля поиск ПВЗ в модалке падал с `apiship_escape is not defined` — браузер держал старый `apiship_order.js` (сервер отдаёт его с кешем на 30 дней). Теги script в админке получили параметр `?v=` с временем изменения файла.
* OpenCart 4, память: карта ПВЗ на больших городах (Москва, 10 000+ точек) падала с `Allowed memory size exhausted` при записи справочника точек в кеш. У API запрашиваются только нужные модулю поля точки (параметр `fields`), строки обрезаются до них сразу после получения, точки уже известные из кеша повторно не запрашиваются (у API берутся только недостающие id), индекс точек в кеше разбит на шарды по id (до 96 000 точек на магазин, при переполнении старые вытесняются) и пишется один раз за загрузку, отдельный кеш по набору id убран. Замер на 12 000 точек с memory_limit 128M: было падение, стало 62 МБ пиковых. В лог пишется `x_tracing_id` каждого запроса lists/points.
* OpenCart 4, безопасность: cron-эндпоинты экспорта и импорта статусов принимают только POST, ключ передаётся заголовком `X-Apiship-Key` (или полем `key` в теле), в URL ключ больше не передаётся — cron-команды в настройках модуля перегенерированы. Действия из админки (выгрузка, отмена, ярлыки, акты, параметры) вынесены в admin-контроллер под сессией администратора: нужны права на маршрут `extension/apiship/sale/order` (выдаются группе установившего, другим группам — вручную в Группах пользователей, см. README) и право на изменение заказов; cron-ключ в html админки не попадает. Пришедшие от API строки (названия ПВЗ, тарифов, адреса, ссылки на файлы) экранируются в чекауте и в админке.
* OpenCart 4, скорость: кеш справочников API общий для всех покупателей магазина (ключ по токену) и живёт 6 часов; ответ карты ПВЗ отдаёт только нужные карте поля (в 2 раза меньше трафика); соединение с API переиспользуется (keep-alive, gzip); при постраничной загрузке ПВЗ не делается лишний пустой запрос; выбранный ПВЗ ищется по индексу в кеше без повторного скачивания списка.
* Исправлено (OpenCart 4): справочники API (расчёт, точки, списки) кешируются в кеше OpenCart, а не в сессии. Сессия OC4 хранится в БД одной JSON-строкой (колонка text, 64 КБ): у магазинов с несколькими службами доставки список ПВЗ переполнял её, MySQL обрезал JSON, и ядро теряло адрес доставки — «Ошибка расчета стоимости» при выборе ПВЗ, невозможность оформить заказ.
